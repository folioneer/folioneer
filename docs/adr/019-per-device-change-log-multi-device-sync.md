# ADR 019 — Per-Device Change Log for Multi-Device Sync

**Date**: 2026-08-22
**Status**: Accepted

## Context

Multi-Device Sync (SYN) lets several desktop installations converge on one portfolio. The transport is a folder the user already synchronises with a cloud client (Dropbox, Drive, OneDrive, Syncthing); the application never touches the network, and everything it writes into the folder is encrypted on the device. That transport has one hard property: a cloud client moves files well but resolves two machines writing the **same file** badly — conflicted-copy duplicates at best, a corrupted SQLite file if a sync lands mid-write at worst. The data is a financial ledger, so a lost or duplicated entry that goes unnoticed for weeks is the failure mode to design against. Usage is one device at a time in practice but not guaranteed, and a phone may join later.

## Decision

Each device records every creation, update, and removal of a synced record as a **change** (device, per-device sequence, record kind, record id, operation, full content), publishes its own changes as append-only **segment** files inside its own area of the folder, and applies other devices' segments from a per-device **cursor**. Published history is complete and never pruned; a newcomer replays it in full — a personal portfolio's history is a few kilobytes a month, so checkpoints and pruning are deliberately left out of the first version. Transactions merge by union; every other synced record (accounts, categories, assets, currency pairs and rates, holding notes) merges later-change-wins with a deterministic tiebreak (consistent with ADR-012); derived data (ADR-013) and device-local data are never synced. Capture is **hand-rolled**: a `ChangeRecorder` port in the shared infrastructure layer, injected into every repository that writes a synced record, appends the change row on the **same database connection and transaction** as the write — so the record and its change exist together or not at all (SYN-020). The port lives in infrastructure rather than domain because it takes the live connection; the sync bounded context implements it. (ADR-006's unit of work, which this decision first cited, has no implementation in the codebase — tracked in `docs/techdebt.md`.) Every merge outcome — which change prevails, what is held back, discarded, or marked inconsistent — is decided by **one backend resolution component** implementing the Sync Conflict Resolution spec (CFR) and nothing else; no repository, use case, or frontend code decides a merge outcome, and the frontend only displays results. A change to the conflict rules is therefore a change to that one component.

Alternatives considered: (a) **whole-database encrypted snapshot** — far simpler and its failures are loud, but either one shared file (the cloud-client hazard above) or immutable per-sync files that silently discard one device's work whenever both were edited between syncs, and a rewrite if a phone joins; (b) **SQLite triggers** for change capture — no call sites to forget, but invisible in the codebase, must be suppressed during replay, and the user rejected any SQL-level dependency; (c) a **post-commit event-bus listener** — rejected because the bus publishes after commit and its events carry no record identity, so atomicity and traceability are both lost; (d) a **CRDT library** (cr-sqlite / Automerge) — correct merge semantics out of the box, but invasive on an existing schema and a heavy dependency for a single-user app whose concurrency is low. The domain already derives holdings by replaying transactions, so an append-only log is the natural fit and requires no event-sourcing rewrite of existing tables.

## Consequences

- **Pros**: conflict rules live in one Rust component, so the CFR spec maps one-to-one onto a single testable unit; no file is ever written by two machines, so ordinary cloud clients are safe; no silent loss — both devices' edits survive a lapse in one-device-at-a-time discipline, and an edit that is overruled is surfaced; steady-state sync reads a few small files; the same model extends to a phone rather than being replaced; capture is explicit in the repositories and testable without database-level machinery.
- **Cons**: more to build than a snapshot — a change record, cursors, logical ordering (wall-clock alone is never sufficient across devices), permanent tombstones for removals, and a data-format version gate; the folder grows without bound until a later version adds checkpoints; every write path on a synced record must append a change — 28 repository sites across account, asset, and currency at adoption — and a missed path diverges devices silently (a reviewer-checked invariant, not a runtime guard); merge correctness rests on the project's own tests rather than a library's; union merge applies no holding validation, so two independently valid sales can oversell a position after merge — the merged ledger is kept and the holding is surfaced as inconsistent until the user resolves it (CFR-042, SYN-040), a new state the interface must carry; the folder host can observe file names, sizes, and times even though it cannot read content.
