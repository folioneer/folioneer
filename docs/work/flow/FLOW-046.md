# FLOW-046 — The rule on sorting and filtering puts every view choice in the core

- Kind: quality
- Observed: the owner, 2026-10-18, on TODO-091's "group by wrapper": F32 (`docs/frontend-rules.md`) makes the core group, order and filter everything a screen shows, and A12 (`scripts/arch-check.py`) fails on any new `.sort(` / `.filter(` in feature code. That was a mistake: the core decides the answer, each facade (the window, a CLI, the MCP tools) decides how to look at it. Data-grid guidance agrees on the condition — a client sorts and filters only a set it holds whole; a paged set is sorted and filtered on the server.
- Proposal: F32 is rewritten as: **the core decides what the answer is** — the records in scope (by identifier, period, state, date), every figure and flag a business rule decides, and any order that carries meaning (as the row order or a rank field); **the facade decides how to look at it** — sort, search, filter, group, show or hide — on the fields of rows it received, over a set it holds whole, never by a value it works out itself. Test: two facades may legitimately differ, and the user undoes it without asking the core again. A12 tells the two apart mechanically (for instance: sorting and filtering only through one shared table helper, a computed figure still caught); the reviewer prompts (`reviewer-frontend`, `reviewer-arch`) follow; DEBT-046–053 are re-read and the sites that are view choices leave `arch-allowlist.json`.
- Costs: M — the rule, the architecture check with its script tests, two reviewer prompts, the allowlist. Protects: business rules stay in the core while each facade shapes its own view, and reviewers stop asking the core for presentation.
- Needs the owner: no — the rule above is the owner's, validated 2026-10-18.
