# 2026-10-11 — DEBT-120 — What moving the portfolio to a folder that holds none leaves open

- Found by: `reviewer-backend` and `spec-reviewer` on DEBT-106's pull request (2026-10-11); each point read again in the code by the main agent
- Where: `publish_as_origin` in `src-tauri/src/context/sync/application/first_publish.rs`; the header gate in `src-tauri/src/context/sync/application/run.rs`; the "Change folder" action of the sync page
- Severity: 🟡
- Observation: three things. **Forgetting is a second write.** An origin's enrolment commits — device row, folder, numbering — and only then are its cursors, held-back changes and conflict notices deleted, in a write of their own: should that write fail, the action answers an error and the device has moved all the same, with what it kept of the history it left; starting over had the same order before. In a folder that holds no other device's area those rows match nothing. **A header of another beginning under the same key is seen only when a folder is designated.** A sync run checks a header by its passphrase check alone (SYN-084): a device whose own folder came to hold the portfolio as another device moved it — the files replaced by hand — would publish there and read the origin's area from its old cursor. Not run. **The move asks nothing.** Since DEBT-106 the other computers rejoin from a fresh installation after a move, as after starting over; starting over says so and asks to confirm (SYN-071), "Change folder" does not
- User value: A portfolio moved to another folder never leaves a computer syncing against a history that is not its own, and the owner is told what a move costs the other computers before making it.
- Done when: the forgetting commits with the enrolment or cannot leave the device half-moved; a run refuses a header of another beginning as it does a reset, with a test; the owner has said whether a move to a folder that holds no portfolio is confirmed, and the window does what was said.
