# Business Rules — AI Agent Connection (AGT)

## Context

An AI agent — Claude Code, Claude Desktop, any program that speaks the Model Context Protocol — may read the portfolio and record in it through the application its owner has opened. The AI agent starts the installed program with `--mcp`; that process is a **bridge**: it holds no data and passes each tool call to the running application (ADR-023). The **channel** is what the application listens on; a **connection** is one bridge's link to it. The running application asks its owner before serving a connection and runs every tool through the queries and the recording rules the window uses. A tool behaves as the window does, whoever calls it — the window, the command line or an AI agent: the same use case, the same rules, the same refusals with the same codes (owner, 2026-10-20). What an AI agent may not do alone is security: it changes, removes or replaces a transaction the owner typed only with the owner's answer in the window (AGT-080, AGT-087, AGT-090). The other departures are named where they are made: an AI agent names what it means by text, read and refused before the window's rules (AGT-042, AGT-048, AGT-055), and never names the cash, as the command line (CLI-011); a fee its holding's schedule generated is not recorded twice (AGT-067); `request_change` does not take a write-off's reason (AGT-087); `add_account` bounds the name and the bank and takes no management-fees setting (AGT-068). Nothing answers when the application is closed or when the owner's setting is off. The text an AI agent reads is English, like the command line's.

The AI agent connection exists on Linux and other Unix systems, and on Windows. A system without a local channel of either kind has none (AGT-023).

## Business Rules

### The bridge (010–019)

**AGT-010 — The bridge speaks the Model Context Protocol (backend)**: The program started with `--mcp` reads JSON-RPC messages, one per line, on its standard input and answers on its standard output until the input ends. It answers `initialize` (with the protocol version the AI agent asked for, the capability `tools`, and its name and version), `ping`, `tools/list` (the tools of AGT-046, each with a title, a description, the JSON schema of its arguments and whether it only reads — AGT-013) and `tools/call`; a notification takes no answer; any other method, and a call of a tool it does not list, is a JSON-RPC error. A line that is not JSON is skipped.

**AGT-011 — No application, no answer (backend)**: The bridge opens no database and reads no file of the portfolio (ADR-023). When no application answers on the channel — it is closed, or its setting is off — the bridge still introduces itself and lists its tools, and a tool call is answered with a refusal saying that Folioneer is not open or that AI agents are not allowed to connect.

**AGT-012 — `--mcp` starts the bridge (backend)**: `--mcp` as the program's first argument starts the bridge and nothing else: no window, no command of the command line (CLI-010), no scheduled download. Anywhere else among the arguments it does not start the bridge: the first argument decides, as CLI-010 says.

**AGT-013 — Each tool has a title and says whether it only reads (backend)**: In the list of tools, whatever the protocol version the AI agent asked for, each one carries a `title` — a few English words the owner reads in the AI agent client, "Record a purchase": never empty, and no two tools share one — and, under `annotations`, `readOnlyHint`: true for a tool that only reads the portfolio (AGT-040, AGT-070, AGT-071, AGT-075, AGT-072), false for every tool that records, corrects, cancels, adds, replaces, or asks to remove, to change or to replace (AGT-044, AGT-050, AGT-060, AGT-062, AGT-063, AGT-064, AGT-065, AGT-065A, AGT-066, AGT-080, AGT-087, AGT-090, AGT-093). It is what lets an AI agent client ask the owner before a recording and not before a read; the owner's consent in the window (AGT-032) does not depend on it. The same statement decides what counts as a read of the session (AGT-052), so a tool is never a read for the client and a recording for the window. No other annotation is given: a client reads the absent ones by the protocol's defaults.

### The channel (020–029)

**AGT-020 — One request, one answer, one line (backend)**: The bridge and the application exchange JSON objects, one per line: the bridge asks to connect or calls a tool; the application answers that the connection is granted, with a tool's result, or with a refusal carrying a code and a reason. The code stays on the channel: the bridge passes the AI agent the reason, which is a full sentence, so a rule that names a refusal's code names what the application answers, not what the AI agent reads. A line that is no such object, or that is longer than 4 MiB — a tool's result included — ends the connection.

**AGT-021 — The channel is the owner's user's alone (backend)**: On Linux and other Unix systems the channel is a socket in a folder of the application's data folder. The folder is created for the owner's user alone (no permission for the group or for others), whatever the data folder allows, so no other user's program can reach the socket — the one thing of the data folder the bridge opens. On Windows the channel is a named pipe: its access list names the owner's user and nobody else, so the system refuses any other user's program that tries to open it, and it refuses clients of another computer; its name is drawn at each opening and written to a file of the same folder of the data folder, the one thing of the data folder the bridge opens. There the folder is not closed further: it takes the access list of the data folder, which is the owner's alone where the system puts it. The bridge opens only a name made of `\\.\pipe\folioneer-agent-` followed by letters, digits and dashes, and reads at most 256 bytes of the file. On both systems the application checks that the program at the other end runs as the same user and turns away one that does not, which is written to the log; on Windows the bridge checks the same of the program that answers, so a pipe another user opened under a name left by an earlier run is not spoken to. A file that names no pipe of the channel, or a pipe another user's program answers on, is to the AI agent an application that is not open (AGT-011). The channel is never a network port.

**AGT-022 — The channel exists only while the owner allows AI agents (frontend + backend)**: The setting "Allow AI agents to connect" is off until the owner switches it on, and is kept on this computer across restarts. With it off no channel exists. Switching it on opens the channel; the application opens it at start when the setting is on. Switching it off removes the channel and ends every grant (AGT-035). The Settings dialog shows the setting with what it means.

**AGT-023 — A system without a channel has no AI agent connection (frontend + backend)**: Linux, the other Unix systems and Windows have a channel (AGT-021); the rule holds for a system the channel is not written for. Where the application has no local channel, the setting cannot be switched on (`NoAgentChannel`), the Settings dialog shows it disabled and says the AI agent connection is not available on this system yet, and the bridge answers as AGT-011 says.

**AGT-024 — A channel that cannot be opened leaves the setting off (backend)**: A socket left by an earlier run — on Windows, the file naming its pipe — is replaced; so is, on Windows, a name whose pipe another user's program answers on. The channel is not opened in four cases: its folder is a symbolic link (on Windows, a junction too), its folder cannot be created, its socket — or its pipe, or the file naming it — cannot be created, or a running application of the owner's user still answers on its socket or its pipe — that application keeps its channel. On Windows two applications opening at the same moment are told apart by a lock on the file naming the pipe: the second finds the first one's pipe. Switching the setting on is then refused with `AgentChannelFailed`, the setting stays off, and the cause is written to the log. At start, with the setting kept on, the same cases leave the setting as it is and no channel: the cause is written to the log, and nothing listens until the application starts again or the owner switches the setting off and on. An application that opened no channel removes none when it closes.

### Consent (030–039)

**AGT-030 — A connection waits for the owner (backend)**: The bridge asks to connect at an AI agent's first tool call, under the name the AI agent gave for itself. The application answers only when its owner has: nothing is granted by default or after a delay, and the AI agent's call waits as long as the owner's answer does. An AI agent that goes away before the answer withdraws its request.

**AGT-031 — Nothing runs before the owner allowed (backend)**: A tool call on a connection the owner has not allowed is refused and reaches no tool. A refusal ends that request; the bridge then closes its connection, so the AI agent's next call asks again.

**AGT-032 — The owner allows or refuses in the window (frontend + backend)**: While an AI agent waits, a dialog shows over whatever view is open: the AI agent's name, the user it runs as — the application's own, the only one whose programs can connect (AGT-021) — the time it asked, what a yes covers — reading the accounts, the assets, the holdings, the transactions (AGT-070), the prices (AGT-071, AGT-075) and the totals, adding what the portfolio does not have yet, in one line that names neither accounts nor assets, counted in the same limit (AGT-064, AGT-068), and recording transactions and prices, in one line that names no kind of transaction — every recording tool is covered, the ones to come included (owner, 2026-10-19) — up to the session's limit (AGT-044, AGT-060, AGT-062, AGT-063, AGT-065, AGT-047) — that one answer covers the whole session, and what it never covers: changing or removing a transaction the owner typed — the session corrects or cancels what an AI agent recorded, in this session or an earlier one (AGT-050), and for a transaction the owner typed it can only ask, one at a time (AGT-080, AGT-087) — and reading a file, a setting or the sync folder. Its two actions are "Allow for this session" and "Refuse". It is easy to refuse and hard to approve blindly: refusing is the filled action and has the focus; "Allow" is inactive for a moment after the dialog appears; the keyboard's focus stays on the two actions; and the dialog closes only by an answer — neither its corner nor its backdrop dismisses it. A refusal gives the AI agent nothing: its call is answered that the connection was refused. Several AI agents waiting are shown one at a time, oldest first.

**AGT-033 — One grant covers the session (frontend + backend)**: Once allowed, the AI agent's calls on that connection are served without another question, and each is counted. While an AI agent is connected the header says so — "{agent} is connected" — on every view; a long name is shown cut, with the whole name as its hint. Nothing of a grant is remembered once the session ends, except on what it recorded (AGT-045).

**AGT-034 — The owner disconnects, or the AI agent leaves (frontend + backend)**: The header offers "Disconnect" beside each connected AI agent. Disconnecting closes that AI agent's connection, before anything it already sent is read: its next call is answered that Folioneer closed the connection, and the one after asks to connect again. The channel and the other AI agents' connections are untouched. An AI agent that goes away ends its own session.

**AGT-035 — Closing the application or the setting ends every grant (backend)**: When the setting is switched off, every request is refused, every session ends, every connection is closed — one that had not asked yet included — and the channel is removed, the file naming the pipe with it. When the application closes, the requests, the sessions and the connections end with it; the socket file, or the file naming the pipe, may stay, answers nothing — a bridge that tries it is told the application is not open (AGT-011) — and is replaced at the next start (AGT-024). No request is shown and no session opens afterwards, even for an answer given at that moment.

**AGT-036 — The window shows what the core holds (frontend + backend)**: The window reads the state of the AI agent connection (see Entity Definition). Every change — the setting, a request, a session, a tool call, the owner's removal of what a session recorded (AGT-053), a removal, change or replacement request arriving, answered or withdrawn (AGT-081, AGT-088, AGT-091) — publishes `AgentConnectionChanged`, on which the window reads the state again. Each write publishes its own event before that: `AccountUpdated` for a created account, its mark written (AGT-069); `AssetUpdated` for an added asset; `TransactionUpdated` for a recording, a correction, a cancelling, each transaction of the owner's removal (AGT-053), the transaction removed on the owner's answer (AGT-081), the transaction changed on the owner's answer (AGT-088), the four removed and the transfer recorded on the owner's answer, once (AGT-091), and without one, once (AGT-093); `AssetPriceUpdated` for a price. A recording that cannot be marked publishes its event when it is written and again when it is undone, though the call is refused (AGT-049). The window is told every one, in order, as it is told what the owner types: a view that shows what was written shows it at once, without the owner leaving it and coming back (B45).

**AGT-037 — An AI agent's name is text the application did not write (backend)**: The name an AI agent gives is cleaned before it is shown or logged, by the bridge and again by the application, since a program may speak to the channel without the bridge: control characters and the invisible characters that reorder or hide text are removed, it is cut to 60 characters, and an empty one becomes "An AI agent".

**AGT-038 — Limits (backend)**: At most 8 bridges are connected at once and at most 4 AI agents wait for the owner's answer; one more is turned away, and its call is answered as a refusal. A connection that has not asked to connect within 30 seconds is closed.

**AGT-039 — An answer that comes too late (frontend + backend)**: Answering a request that was withdrawn is refused with `ConnectionRequestGone`; disconnecting a session that already ended, with `SessionAlreadyEnded`. The window says so and reads the state again.

### Tools (040–049)

**AGT-040 — The read tools (backend)**: A connected AI agent may call four tools, each a query the window makes, answered as JSON text: `portfolio_summary` — each account with its total value, its unrealized gain, its performance this year and how many of its prices are outdated, and the portfolio total (ACC-021, ACC-027, MKT-206), without the mark of an account an AI agent created (AGT-069), which names a session's key; `list_accounts` — the accounts by name with their currency (CLI-018), their country and their wrapper (ACC-042; the command line's list is unchanged); `list_assets` — the assets a holding can be of, never a Cash Asset, with the fields of the command line's asset rows (CLI-021), the archived ones too when `archived` is true; `list_holdings` — the holdings of the account named by `account` with their figures, each holding's unrecorded splits (MKT-231), each with its date, `new` and `old`, oldest first, and whether its price is outdated — both without `as_of` only — and the account's totals (ACD, MKT-206), as they stood on the date `as_of`, today or earlier, when it is given. Amounts and quantities are the core's micro-units, which each description says. The schemas declare no other argument; one that arrives all the same is ignored.

**AGT-041 — Every call is written to the log (backend)**: Each tool call is written to the application's log with its session, its tool and whether it was refused; a connection allowed or refused is written with the AI agent's cleaned name (AGT-037).

**AGT-042 — A refusal names only what the AI agent sent (backend)**: The reason of a refusal repeats what the AI agent sent and never lists the accounts or the assets that exist — the list tools are how to ask.

**AGT-043 — The refusals of the read tools (backend)**: `list_holdings` names its account by its name, case ignored: a name that matches no account is refused with `AccountNotFound`, one that two accounts share with `AccountAmbiguous`, a missing one with `MissingArgument`; an `as_of` that is not a date, or is in the future, with `InvalidDate`. A read that fails is refused with `DatabaseError`, in any of the four tools.

**AGT-044 — Opening balances, purchases and sales (frontend + backend)**: A connected AI agent may record what the command line records, through the same recorder and the same rules as the window (CLI-012): `record_opening_balance` — the quantity and the total cost of what an account already held (TRX-047); `record_purchase` and `record_sale` — a quantity with either the unit price in the asset's currency or the broker's all-in total in the account's currency (CLI-013), and optionally fees, an exchange rate and a note of at most 500 characters. Each names its account by name and its asset by name, reference, ISIN or reference with its exchange (CLI-011). What is left out is as on the command line (CLI-014): the date is today, the fees 0, the rate 1. A recording is answered with the transaction as recorded, its account, its currency and its asset. The window shows it as it happens, by the event every recording publishes.

**AGT-045 — What an AI agent recorded is marked (frontend + backend)**: A transaction an AI agent recorded is marked with the AI agent's name, the key of its session and the time that session started; a transaction without a mark is one the owner typed, one an account import recorded, an added deposit among them, one an AI agent recorded on another of the owner's computers — the mark is kept on the computer that recorded it and is not sent to the others — or, should both the marking and its undoing fail, the one AGT-049 names. The rows of the account journal carry the mark (TXL-060), and the journal shows it in a column "Recorded by": the AI agent's name, with "{agent} · session of {date and time}" as its hint (TXL-061). The mark goes with its transaction: correcting the transaction keeps it, removing the transaction removes it. An imported row counts as the owner's wherever this spec speaks of what the owner typed (AGT-080). The chip the journal shows for an added deposit (IMP-051) is no AI agent's mark (IMP-054).

**AGT-046 — No other tool exists (backend)**: The tools are the four of AGT-040, the one of AGT-070, the one of AGT-071, the one of AGT-075, the one of AGT-072 (with AGT-073 and AGT-074), the three of AGT-044, the two of AGT-050, the three of AGT-060, the two of AGT-063, the one of AGT-065, the one of AGT-065A, the two of AGT-066 (with AGT-067), the one of AGT-062, the one of AGT-064, the one of AGT-068 (with AGT-069), the one of AGT-080, the one of AGT-087, the one of AGT-090 and the one of AGT-093. Nothing corrects or deletes a transaction with no mark — a transaction the owner typed is removed, changed or replaced only by the owner's answer (AGT-080, AGT-087, AGT-090) —, changes or deletes an account, changes or removes an asset, or takes or returns a path, a setting or anything of sync.

**AGT-047 — A session records up to a limit (backend)**: One session records at most 500 transactions and prices (AGT-062), the accounts it creates and the assets it adds counted with them (AGT-068, AGT-064), in all. The next recording, account created or asset added is refused with `SessionLimitReached`, which says the owner disconnects and allows a new session to go on; reading is not limited.

**AGT-048 — The refusals of a recording (backend)**: Figures are decimals with a dot and at most six decimals, as text or as JSON numbers — a JSON number in exponent form (`2e-6`) is read as the decimal it stands for, which then holds at most six decimals (`2e-7` is refused), while text in exponent form is refused; a figure too large to hold (`1e30`, `99999999999999999999`) is refused in any form; anything else is refused with `InvalidFigure`; a missing figure, account or asset with `MissingArgument`. An argument a recording does not know is ignored, as for the read tools (AGT-040). A price together with a total, or neither, a `date` or a `note` that is not text, a note longer than 500 characters, and a note holding a control character other than a line break (LF, or CR LF — a tab is refused), or one of the invisible characters that reorder or hide text (AGT-037), are refused with `InvalidArguments` — a date that is not text is never read as today. Every other refusal is the recording's own, with its code and its reason: the account or the asset not found or ambiguous (CLI-011), a date that is text but not a date (`InvalidDate`) or is in the future (`DateInFuture`), an oversell, and the rest of the window's rules (CLI-012).

**AGT-048A — Text an AI agent sends is bounded (backend)**: The note of a recording or a correction is shown to the owner as the AI agent wrote it (AGT-048). Every other text argument of every tool — a name, a reference, an id, a date, a kind — longer than 200 characters is refused before the core reads it, with `InvalidArguments`, or `InvalidDate` where the tool refuses a date that way (AGT-043); a shorter limit of the tool's own (AGT-064) still holds.

**AGT-049 — A recording that cannot be marked is undone (backend)**: Recording and marking are one operation of the core, which runs to its end once started: a disconnect or a closing application never stops it between its two writes. When the mark cannot be written the recording is undone and the AI agent is refused with `NotRecorded`: nothing was recorded. Should the undoing fail too, the refusal is `RecordedNotMarked`, which says the transaction was recorded and tells the AI agent to tell the owner; both failures are written to the log, and that transaction counts against the session's limit (AGT-047).

### Corrections and removals (050–059)

**AGT-050 — A session corrects and cancels what an AI agent recorded (backend)**: A connected AI agent may call two more tools, each naming a transaction by its id, as its recording returned it or `list_transactions` gives it (AGT-070): `cancel_recording` removes it, and `correct_recording` changes it, whatever its type — but a part of a transfer (AGT-065A) —, given what changes as AGT-055 states: what is given replaces what was recorded and the rest stays. The id is text, and a missing one is refused with `MissingArgument`. Both tools then run through the window's correction — TRX-031 and the correction of each type's own spec — and deletion (TRX-034), and are refused with their codes; a correction publishes `TransactionUpdated`, as the window's does. Like a recording (AGT-049), a correction or a cancelling runs to its end once started. Neither gives a place back of the session's limit, and a correction takes none (AGT-047).

**AGT-051 — A session touches only what an AI agent recorded (backend)**: The two tools take any transaction with a mark on this computer (AGT-045), whichever session recorded it, an earlier session or another AI agent's included (owner, 2026-10-25). They are refused with `NotYourRecording` for a transaction with no mark, the owner's (AGT-080), and for one that does not exist; the reason is the same sentence in both cases, so it says nothing of what exists (AGT-042), and it names the three tools that ask the owner (AGT-080, AGT-087, AGT-090). A correction keeps the transaction's mark: nothing records which session last changed it (owner, 2026-11-01).

**AGT-052 — The window is told what a session did (backend)**: With each session the state (AGT-036) carries when the owner allowed it, how many of its calls of a read tool (AGT-013) were answered, how many of the transactions it recorded still exist — whatever removed the others: the session, another session, the owner's removal (AGT-053) or a deletion in the journal — and, of those that exist, the type, the asset's reference and the date of the one it recorded last, as they stand after any correction. The two are read from the portfolio after each recording, correction, cancelling and replacement (AGT-093) of the session and after the owner's removal, so a deletion made in the journal, or by another session, shows at the next of these. The window is told after every call and after the owner's removal.

**AGT-053 — The owner removes everything a session recorded (backend)**: For a session that is still connected the owner can remove, in one action, every transaction it recorded and that exists when the action starts, and nothing else: each goes through the deletion of the window (TRX-034), the last recorded first, and one the deletion refuses is tried again once the others are gone. What the deletion still refuses — a recording that a transaction recorded since depends on, the owner's or another session's — is kept and counted, and the action answers how many were removed and how many kept; a recording the session makes while the action runs stays, and counts in what the window is told afterwards. For a session that has ended, or that never was, the action is refused with `SessionAlreadyEnded` and nothing is removed (AGT-039). When the portfolio cannot be read or written the action fails with `DatabaseError`; what it removed before stays removed, and the window is told what is left. Once the session has ended its recordings stay marked in the journal (AGT-045) and are removed one by one there.

**AGT-054 — The session dialog (frontend)**: In the header, "{agent} is connected" (AGT-033) opens a dialog on that session, over the whole window. It shows since when the AI agent is connected, how many of its calls of a read tool were answered — shown as requests — on a row "Accounts added" above the assets' row, how many accounts it created with the name of the last one, or that it created none (AGT-068), how many assets it added with the name and the reference of the last one, or that it added none (AGT-064), how many transactions it recorded that still exist, and its last recording — its type, the asset's reference and its date — or that there is none (AGT-052); the figures follow the state as it changes (AGT-036). Its three actions are "Remove everything it recorded", "Close" and "Disconnect" (AGT-034); a sentence says what the first removes — the session's recordings as they stand, a correction the owner made to one of them included, and no transaction the owner recorded — and that it asks to confirm. The sentence speaks of transactions only: it does not name the accounts the session created or the assets it added, which the removal leaves (AGT-068, AGT-064). With no recording left the removal is inactive and the sentence says so. Removing asks in a second dialog, which names the AI agent and the number of transactions as it stands then: keeping them is the filled action and has the focus, and only "Remove" there removes (AGT-053). The removal runs behind the session dialog, whose actions stay active. What it did is said in a snackbar: how many transactions were removed and, when some were kept, how many, because a transaction recorded since depends on them. A refusal (`SessionAlreadyEnded`) or a failure (`DatabaseError`) is said in a snackbar too, and the state is read again: after a failure the dialog's figures show what is left. Both dialogs close when the session ends. A connection request that arrives meanwhile takes their place until it is answered (AGT-032).

**AGT-055 — What a correction takes (backend)**: `correct_recording` takes what the window's correction of the transaction's type takes: a `date` and a `note` for every type; for a purchase or a sale a `quantity`, a `price` or a `total` (never both), `fees` and a `rate`; for an opening balance a `quantity` and a `total`, its total cost; for a deposit or a withdrawal an `amount`; for a dividend an `amount`, in the asset's currency, and a `rate` (DIV-040); for a split `new` and `old`, its ratio as `record_split` reads it (AGT-063); for free shares, interest or a write-off a `quantity`, and for a management fee a `quantity`, the quantity removed (FEE-063); for a write-off also its `reason`, as `record_write_off` reads it (AGT-065). The figures, the `date` and the `note` are read as a recording's (AGT-048), and an argument not named above — a recording's own, such as `percent`, `account` or `asset` — is ignored (AGT-040). A correction is not checked against a fee the holding's schedule generated: FEE-063 has no such guard, and AGT-067 guards recording only. For a purchase or a sale, when neither a price nor a total is given, the stored total is kept, taken as a typed total (TRX-061), while nothing it is made of changes, and a new quantity, new fees or a new rate make it follow the unit price instead (TRX-026); an opening balance's total cost changes only by a new total. Before anything is changed, a correction that gives nothing to change is refused with `MissingArgument`, and with `InvalidArguments` both a price and a total, one part of a split's ratio without the other, and one of the arguments above that the type does not take, the reason naming those it takes. These are answered after AGT-051, so a refusal that depends on the type is given only for a transaction an AI agent recorded.

### Cash, dividends, prices, splits, free shares, assets, write-offs, interest, management fees and accounts (060–069)

**AGT-060 — Deposits, withdrawals and dividends (backend)**: A connected AI agent may record three more transactions, through the same recorder and the same rules as the command line (CLI-027, CLI-028): `record_deposit` and `record_withdrawal` — an account by its name and an amount in the account's currency, and no asset; `record_dividend` — an account, a paying asset named as in AGT-044, the total net amount received in the asset's currency and optionally the exchange rate to the account's currency (default 1, CLI-014). The refusals are the window's (CLI-012), among them `AmountNotPositive`, `InsufficientCash` for a withdrawal that would leave the account's cash below zero, today or at any point from its date on (CSH-031, CSH-080), and `AssetNotHeld` for a dividend of an asset the account does not hold today, whatever the date (DIV-011).

**AGT-061 — Only an opening balance, a purchase or a sale is corrected (backend)**: _Retired._ `correct_recording` corrects every type a session records, as the window does (AGT-050; owner, 2026-10-20).

**AGT-062 — A price at a date (backend)**: A connected AI agent may call `record_price` — an asset named as in AGT-044, the price of one unit in the asset's currency, and optionally a date (default today); it names no account. The figure and what is missing are read and refused as a recording's (AGT-048), and so is a date that is not text. **AGT-063 — Splits and free shares (backend)**: A connected AI agent may record two more transactions, through the same recorder and the rules of the window: `record_split` — an account and an asset named as in AGT-044, and the split's size as a ratio, `new` shares for every `old` shares held, of which the factor recording stores is made as in the window (SPL-062) — and `record_free_shares` — an account, an asset and the quantity received, a figure read as a recording's (AGT-048). The other refusals are the window's, with their codes, among them: for a split, `SplitFactorIsOne`, `SplitCollapsesPosition`, `ClosedPosition` and `CascadingOversell` (SPL-011, SPL-021, SPL-022); for free shares, `QuantityNotPositive` (FSD-011); for both, `AssetNotHeld` for an asset the account does not hold today, whatever the date. **AGT-064 — An asset the portfolio does not have (frontend + backend)**: A connected AI agent may call `add_asset` — a name, a reference, a currency and either a kind, a class or both, and optionally an ISIN and the MIC code of an exchange; kind, class and exchange are read with case ignored. The tool takes no other argument, and one that arrives all the same is ignored (AGT-040). A name, a reference or a currency that is missing, empty or not text, and neither kind nor class, are refused with `MissingArgument`. The name and the reference are text an AI agent wrote that the portfolio keeps and the window shows: a name longer than 100 characters, a reference longer than 30, and either holding a control character or one of the invisible characters that reorder or hide text (AGT-037) are refused with `InvalidArguments`. So are a kind or a class that is not one of those above, `Cash` included, and a kind, a class, an ISIN or an exchange that is not text. The other refusals are the form's, with their codes, among them `AssetAlreadyExists` for an asset the portfolio already has, archived or not (AST-032) — its reason says so and does not name the existing asset (AGT-042) — `IsinRequired`, `IsinNotAllowed`, `ExchangeNotAllowed` and `ClassNotAllowed` (AST-031), `InvalidCurrency`, `InvalidIsinFormat` and `InvalidExchange`. It is answered with the asset as `list_assets` gives it and whether another asset shares its reference (CLI-041), and the window's views of assets show it as it happens, by the event an asset's creation publishes. An added asset takes one place of the session's limit, and at the limit the addition is refused (AGT-047); a refused addition takes none. It carries no mark: the state (AGT-036) says, for the session while it is connected, how many assets it added — additions counted as they are made, whatever becomes of the asset afterwards — and the name and the reference of the last one as it was added; the session dialog shows them (AGT-054), and nothing of it is kept once the session ends. An asset is no transaction: `correct_recording` and `cancel_recording` do not name it, "Remove everything it recorded" leaves it (AGT-053), and the owner edits, archives or deletes it among the assets. The connection dialog names adding what the portfolio does not have yet in what a yes covers, on a line of its own that names neither accounts nor assets (AGT-032).

**AGT-065 — Write-offs (backend)**: A connected AI agent may call `record_write_off` — an account and an asset named as in AGT-044, the quantity that left, a figure read as a recording's (AGT-048), and the reason, one of `NetworkFee`, `Dust`, `Lost` and `Other` by its exact name (WOF entity) — and optionally a date (default today) and a note. The date, the note and what else is missing are read and refused as a recording's, and the account and the asset not found or ambiguous as well (AGT-048). The other refusals are the window's, with their codes, among them `QuantityNotPositive` (WOF-011), `ArchivedAsset` for an archived asset, `ClosedPosition` for an asset not held on the date, `Oversell` for a quantity above what is held then (WOF-010) and `CascadingOversell` (WOF-012). **AGT-065A — Transfers (backend)**: A connected AI agent may call `record_transfer` — `from` and `to`, the sending and the receiving account, each named as an account in AGT-044, `asset`, named as in AGT-044, and `quantity`, what left the sending account — and optionally `received`, what reached the receiving one (default the quantity), `rate`, units of the receiving account's currency for one of the sending one's (default the rate stored for the date, TRF-022), a date (default today) and a note, kept on each part; the figures are read as a recording's (AGT-048). ### More reads (070–079)

Otherwise it is answered as a recording previewed (AGT-072), the transaction keeping its id, and the account read on the evening of the date as corrected, without the correction (the transaction as it stands now) and with it; a corrected transaction keeps its place in the order entered.

**AGT-074 — A price previewed (backend)**: `preview_recording` on `record_price` reads the asset, the date and the price as `record_price` reads them, and is refused as it is (AGT-062). Otherwise it is answered `{"status": "previewed", "price", "asset", "currency", "replaces"}`: the price as it would be recorded and the one already at that date that it would replace (MKT-103), each as `get_price` gives a price (AGT-071) — its date, the price of one unit in micro-units and its source, `Agent` for the one previewed —, or `null` when there is none; the asset's reference and its currency. It moves no holding.

**AGT-075 — An asset's price history (backend)**: A connected AI agent may call `list_prices` — an asset named as in AGT-044, archived or not, optionally `from` and `to`, two dates that bound the prices' dates, both included, and a `page`, a JSON whole number from 1; it names no account, and an argument it does not know is ignored (AGT-040). It reads the prices the application holds for the asset (MKT-072) and writes nothing. The prices the dates keep are answered oldest first, 100 to a page, the first page when none is asked, with the asset's reference and currency, how many prices the dates keep in all, the page and how many pages they make — none when they keep no price; a page past the last holds none. A `from` later than `to`, or dates in the future, keep none and are not refused; an asset with no price in those dates is answered that page, with no price, a total of 0 and no pages: an answer, not a refusal, with no member of its own to say so. Each price carries its date, which is its observation date, the price of one unit in micro-units as stored, and its source, written as in AGT-071. The refusals are a read's: a missing asset with `MissingArgument`, the asset not found or ambiguous (CLI-011), a `from` or a `to` that is not a date — not text included — with `InvalidDate`, a page that is not a whole number from 1 — text of digits included — with `InvalidArguments`, a read that fails with `DatabaseError`. It is a read: it says it only reads (AGT-013), each answered call counts as one of the session's reads (AGT-052), and it takes no place of the session's limit (AGT-047).

### Removal and change requests (080–089)

**AGT-080 — An AI agent asks to remove a transaction the owner typed (backend)**: A connected AI agent may call `request_removal` — a transaction by its id, as `list_transactions` gives it (AGT-070), as text; one that is missing or not text is refused with `MissingArgument`. A transaction the owner typed is one with no mark on this computer (AGT-045): the one `list_transactions` says `owner` recorded. The call is refused before anything is asked with `TransactionNotFound` for an id no transaction has, and with `NotTypedByOwner` for a transaction an AI agent recorded — any session corrects or cancels that with `correct_recording` or `cancel_recording` (AGT-050) — and with `PartOfTransfer` for a part of a transfer: its deletion removes the whole transfer (TRF-040), more than the one transaction the owner is shown (owner, 2026-10-24). Unlike AGT-051, `TransactionNotFound` and `NotTypedByOwner` are told apart: `list_transactions` already says which transactions exist and who recorded each. A portfolio that cannot be read is refused with `DatabaseError`. Otherwise the call waits for the owner's answer (AGT-081) and is answered: `{"status": "removed", "transaction": <id>}` when the owner removed it; `RemovalRefused`, and nothing else, when the owner refused or the session ended first (AGT-082); and, when the owner answered yes and it was not removed, the code and reason of why — `TransactionChanged` for a transaction that no longer stands as the owner was shown it, `TransactionNotFound` for one deleted meanwhile, the deletion's own code for one a later transaction depends on, `DatabaseError`. A session asks one at a time: its connection serves its calls in turn, so its next call waits for this one's answer. Two sessions may ask for the same transaction; once it is removed, the other's yes answers `TransactionNotFound`. The call records nothing and is not counted against the session's limit (AGT-047). Its title is "Ask to remove a transaction you typed".

**AGT-081 — The owner answers each removal (backend)**: While a removal request waits, the state (AGT-036) carries it, oldest first, with the AI agent's name, when it asked, and the transaction as it stood when the AI agent asked: its date, its account's name, its type, its asset's name and reference — none for a transaction on the account's cash —, its quantity as stored — a split's is its factor, as `list_transactions` gives it —, and its total in the account's currency, with that currency. The owner answers in the window: remove it, or refuse. A yes goes through the deletion of the window (TRX-034), and only while the transaction stands as it was shown — the same date, type, quantity and total —; the transaction removed publishes `TransactionUpdated` (AGT-036). The request is gone once answered, whatever came of it, and its AI agent is told (AGT-080). The owner's answer to a request no longer waiting is refused with `RemovalRequestGone`; a yes that removed nothing is refused with `TransactionNotRemoved` and the reason's code as the AI agent is given it, or with `DatabaseError` when the portfolio could not be read or written.

**AGT-082 — Nothing of an answer is kept (backend)**: The session's grant (AGT-032) never covers a removal, a change or a replacement: every one is asked, and an answer covers the one transaction it was asked for — for a change, that one change; for a replacement, those four transactions and that transfer. Nothing of an answer is remembered for the next request, the same transaction's included. A request is withdrawn when its session ends — the owner disconnects it or switches the setting off (AGT-034, AGT-035), and its call is answered `RemovalRefused`, `ChangeRefused` or `ReplacementRefused` before its connection closes — and when its AI agent goes away while it waits (AGT-086).

**AGT-083 — The removal dialog (frontend)**: While a removal request waits and no AI agent waits to connect — a connection request comes first (AGT-032) — a dialog shows over whatever view is open, and the session dialog gives way to it as to a connection request (AGT-054). Its title is "{agent} asks to remove a transaction you typed". It shows the transaction in full, as the state carries it (AGT-081): its date, its account, its type, its asset with its reference, its quantity, and its total with the account's currency. A transaction on the account's cash shows no asset and no quantity. A split's quantity is its factor; a total of 0 is shown as 0. It says what would become of it — removed, the account's holdings and cash recomputed from the transactions that remain — and that the answer covers this transaction only. Its two actions are "Remove this transaction" and "Refuse"; no action covers more than one. Refusing is the filled action and has the focus; "Remove this transaction" is inactive for the same moment as "Allow" (AGT-032); the keyboard's focus stays on the two actions; neither its corner nor its backdrop dismisses it: it closes on an answer, or when its request is withdrawn (AGT-082). Several requests are shown one at a time, oldest first. A removal says nothing more: the views that show the transaction follow it (AGT-036). A yes that removed nothing says why in a snackbar — the transaction changed since the AI agent asked, it no longer exists, or a later transaction depends on it —, as does an answer that came too late or a portfolio that could not be written; the state is read again.

**AGT-084 — The window says what an AI agent records (frontend + backend)**: With each session the state (AGT-036) carries how many transactions it recorded, whatever became of them since — a count that only rises, unlike how many still exist (AGT-052): a price, a created account, an added asset and a refused recording are not counted in it. Whatever view is open, each read of the state that finds this count risen since the last read says the session's last recording in the window's snackbar: "{agent} recorded: {type} · {asset} · {date}" — the transaction's type, the asset's reference and the date, as the session dialog shows its last recording (AGT-054); and each read that finds the session's count of added assets risen (AGT-064) says the last of them: "{agent} added an asset: {name} ({reference})". The AI agent's name is shown as it is held (AGT-037). The recording message names the session's last recording that still exists (AGT-052): when none is left, nothing is said. Several recordings between two reads make one message, about the last. A read says the sessions oldest first, a session's recording before its added asset, and each message replaces whatever the snackbar showed, so the last one said stays. A session that ended before the read is not announced. A correction or a cancelling moves neither count and is not announced, nor is a session the window reads for the first time. A price an AI agent records is not announced: the state does not carry it. Nor is an account an AI agent creates: the session dialog counts it and the accounts list marks it (AGT-068, AGT-069).

**AGT-085 — A call the AI agent gave up on (backend)**: While a call waits, the bridge still hears its AI agent. A cancel (`notifications/cancelled`) naming the tool call being answered, while the bridge holds no grant for its connection, gives that call up: the connection request is withdrawn, so its dialog leaves the window, which shows one only while an AI agent waits (AGT-032, AGT-036); the call takes no answer, and the next call asks again. Once the bridge holds the grant, a cancel changes nothing: the call — a removal, change or replacement request waiting on the owner included (AGT-080, AGT-087, AGT-090) — is answered, and the session stays. When the owner's yes and the cancel cross, the order in which the application reads them decides: a yes read first opens a session that ends as the connection closes (AGT-034). A cancel naming no call being answered is ignored. Anything else the AI agent says while a call waits is answered after it, in order; past 64 such lines the bridge stops reading the AI agent until the call is answered.

**AGT-086 — An AI agent that goes away mid-call (backend)**: An AI agent goes away when its bridge's input ends. While a call waits it ends the bridge: a connection request is withdrawn as when it goes away before the answer (AGT-030), and in a session the call is given up — a removal, change or replacement request it waits on is withdrawn (AGT-082) — and the session ends with its connection (AGT-034). A write already started — a recording, a correction, a cancelling, a price, an added asset — runs to its end (AGT-049); the window is told, and the call is written to the log as given up (AGT-041).

**AGT-087 — An AI agent asks to change a transaction the owner typed (backend)**: A connected AI agent may call `request_change` — a transaction by its id, read and refused as `request_removal` reads it (AGT-080), and what changes, as the window's correction of that type takes it (TRX-031 and the correction rules of each type — CSH-023, CSH-033, DIV-040, SPL-030, FSD-040, INT-040, FEE-063, WOF-030): a `date` and a `note` for every type; for a purchase or a sale a `quantity`, a `price` or a `total` — never both —, `fees` and a `rate`; for an opening balance a `quantity` and a `total`, its total cost; for a deposit or a withdrawal an `amount`; for a dividend an `amount`, in the asset's currency, and a `rate`; for a split `new` and `old`, its ratio as `record_split` reads it (AGT-063); for free shares, a management fee, interest or a write-off a `quantity`, a write-off keeping its reason, which `request_change` does not take. What is given replaces what is stored and the rest stays, a stored total kept or following the unit price as a correction keeps it (AGT-055). The figures, the `date` and the `note` are read and refused as a recording's (AGT-048), and an argument the tool does not know is ignored (AGT-040). Before anything is asked the call is refused: with `MissingArgument` for a missing id, when nothing is given to change, or when the transaction as it would become equals it as it stands in every value the state shows of it (AGT-088); with `TransactionNotFound` and `NotTypedByOwner` as `request_removal` is (AGT-080); with `InvalidArguments` for both a price and a total, for one part of a split's ratio without the other, or for an argument above that the transaction's type does not take, the reason naming those it takes; with each refusal the window's correction gives, checked on the account as it stands with nothing written — among them `CascadingOversell`, `InsufficientCash` and `DateInFuture` —; and with `DatabaseError` for a portfolio that cannot be read. Otherwise the call waits for the owner's answer (AGT-088) and is answered: `{"status": "changed", "transaction": <the transaction as stored after the change>}` when the owner changed it — its id, account, asset, date, type, note and, in micro-units, its quantity, unit price, total, fees and exchange rate, a split's quantity being its factor; `ChangeRefused`, and nothing else, when the owner refused or the session ended first (AGT-082); and, when the owner answered yes and it was not changed, the code and reason of why — `TransactionChanged` for a transaction that no longer stands as the owner was shown it, `TransactionNotFound` for one deleted meanwhile, the correction's own code, `DatabaseError`. A session asks one at a time, as for a removal (AGT-080). The call records nothing and is not counted against the session's limit (AGT-047): a transaction changed on the owner's answer stays the owner's, with no mark (AGT-045), and is counted in none of the session's figures (AGT-052, AGT-084). Its title is "Ask to change a transaction you typed".

**AGT-088 — The owner answers each change (backend)**: While a change request waits, the state (AGT-036) carries it with what a removal request carries (AGT-081) and the transaction as it would become, in the same form. A transaction the state shows — of a removal or a change request — carries its unit price, its fees, its exchange rate and its note besides what AGT-081 names. A change request also names the values the change moves among the date, the quantity, the total, the unit price, the fees, the rate and the note, so the window marks them without comparing (AGT-089). Removal and change requests share one order, oldest first. The owner answers in the window: change it, or refuse. A yes goes through the correction of the window (TRX-031) with what the AI agent asked, and only while the transaction stands in full as it was shown — the same date, type, quantity, total, unit price, fees, rate and note —; the transaction changed publishes `TransactionUpdated` (AGT-036). The request is gone once answered, whatever came of it, and its AI agent is told (AGT-087). The owner's answer to a change request no longer waiting is refused with `ChangeRequestGone`; a yes that changed nothing is refused with `TransactionNotChanged` and the reason's code as the AI agent is given it, or with `DatabaseError` when the portfolio could not be read or written.

**AGT-089 — The change dialog (frontend)**: A change request is shown as a removal request is (AGT-083), in the one order of the requests (AGT-088), with the same keyboard, focus and dismissal rules. Its title is "{agent} asks to change a transaction you typed". It shows the transaction in two columns, "As it is" and "As it would become", with the rows of the removal dialog, and a row for the unit price, the fees, the exchange rate or the note when the change moves it; a value the request names as moved (AGT-088) is struck through in the first and set in the accent colour in the second. The note is text the owner or an AI agent typed, shown as it is. It says what would become of it — changed as shown, the account's holdings and cash recomputed from it — and that the answer covers this change of this transaction only. Its two actions are "Change this transaction", inactive for the same moment as "Allow" (AGT-032), and "Refuse", the filled action in focus. A change says nothing more: the views that show the transaction follow it (AGT-036). A yes that changed nothing says why in a snackbar — the transaction changed since the AI agent asked, it no longer exists, or the correction refused it —, as does an answer that came too late or a portfolio that could not be written; the state is read again.

### Replacement requests (090–099)

**AGT-090 — An AI agent asks to replace four transactions the owner typed with a transfer (backend)**: A connected AI agent may call `request_transfer_replacement` — `transactions`, the ids of four transactions as `list_transactions` gives them (AGT-070), and a `rate` as `record_transfer` reads it (AGT-065A). A `transactions` that is missing or not a list of texts is refused with `MissingArgument`; one that names other than four transactions, or one of them twice, with `InvalidArguments`. Each is read and refused as `request_removal` reads its transaction (AGT-080), with `TransactionNotFound` and `NotTypedByOwner`. The four are a transfer recorded the four-step way when they are a sale and a withdrawal in one account, and a deposit and a purchase in another, the sale and the purchase of one asset, whatever their dates and their amounts; otherwise the call is refused with `NotATransfer`, the reason naming what the four lack. The transfer they become goes from the sale's account to the purchase's, of their asset, on the sale's date, the sale's quantity sent and the purchase's quantity received, at the `rate` given or, with none, at the rate TRF-022 takes for that date, with no note. Before anything is asked it is checked on the two accounts as they would stand — without the four, with the transfer — with nothing written, and refused as the window's transfer is (TRF-010 to TRF-022) — among them `ArchivedAsset`, `TransferReceivedAboveSent`, `TransferRateMissing`, `TransferRateNotOne`, a later transaction left short of units and, with `InsufficientCash`, a later cash debit left short of cash (CSH-024) —, and with `DatabaseError` for a portfolio that cannot be read. Otherwise the call waits for the owner's answer (AGT-091) and is answered: `{"status": "replaced", "transfer": <the transfer as TRF-060 reads it>}` when the owner replaced them; `ReplacementRefused`, and nothing else, when the owner refused or the session ended first (AGT-082); and, when the owner answered yes and nothing was replaced, the code and reason of why — `TransactionChanged` for one of the four that no longer stands as the owner was shown it, `TransactionNotFound` for one deleted meanwhile, the transfer's own code, `DatabaseError`; and `DatabaseError`, its reason saying the transfer was recorded, when it was but could not be read back. A session asks one at a time, as for a removal (AGT-080). The call records nothing and is not counted against the session's limit (AGT-047): the transfer recorded on the owner's answer is the owner's, with no mark (AGT-045), and is counted in none of the session's figures (AGT-052, AGT-084). Its title is "Ask to replace four transactions you typed with a transfer".

**AGT-091 — The owner answers each replacement (backend)**: While a replacement request waits, the state (AGT-036) carries it with the AI agent's name and when it asked, the four transactions as a change request shows a transaction (AGT-088) — the sale, the withdrawal, the deposit, the purchase, in that order —, and the transfer they become: its sending and receiving accounts' names, its date, its asset's name and reference, the quantities sent and received, the cost it moves in the sending account's currency with that currency, and between currencies its rate and that cost in the receiving account's currency with that currency, and the quantity not received when less is received than sent (TRF-021). Removal, change and replacement requests share one order, oldest first. The owner answers in the window: replace them, or refuse. A yes removes the four and records the transfer in one write, as TRF-020 to TRF-022 record it, and only while each of the four stands in full as it was shown (AGT-088) and the transfer, at the rate the owner was shown, still moves the cost shown — otherwise `TransactionChanged` —, checked as before asking (AGT-090): the two accounts then stand as if the transfer had been recorded instead of the four from the start — the same transactions besides the four, holdings, costs, cash, realized results and net cash input. A yes that replaces nothing writes nothing. The four removed and the transfer recorded publish `TransactionUpdated` once (AGT-036). The request is gone once answered, whatever came of it, and its AI agent is told (AGT-090). The owner's answer to a replacement request no longer waiting is refused with `ReplacementRequestGone`; a yes that replaced nothing is refused with `TransactionsNotReplaced` and the reason's code as the AI agent is given it, or with `DatabaseError` when the portfolio could not be read or written.

**AGT-092 — The replacement dialog (frontend)**: A replacement request is shown as a removal request is (AGT-083), in the one order of the requests (AGT-091), with the same keyboard, focus and dismissal rules. Its title is "{agent} asks to replace four transactions you typed with one transfer". Under "The four transactions, removed", the four, one per line and struck through: the account, the date, the type, the asset — "Cash" for a transaction on the account's cash —, the quantity — none on the cash; leaving the holding with a minus, entering it with a plus — and the total with the account's currency, with a plus into the account's cash and a minus out of it. Under "Recorded in their place", the transfer in the accent colour: "From", "To", "Date", "Asset", "Quantity" ("{sent} sent · {received} received") and "Cost moved" ("{cost} {currency}"; between currencies "{cost} {from} = {converted} {to} at {rate}"). Under "What would become of it": "One transfer, as if recorded so from the start: the {asset} keeps its cost in {to}; the withdrawal and the deposit leave both accounts' cash and net cash input; the sale's realized result leaves the gains." When less is received than sent, then: "The {difference} not received is a fee in kind: written off at its cost in {from}." Then: "Your answer covers these four transactions only. The transfer is yours, as if you had typed it." Its two actions are "Replace with the transfer", inactive for the same moment as "Allow" (AGT-032), and "Refuse", the filled action in focus. A replacement says nothing more: the views that show the transactions follow it (AGT-036). A yes that replaced nothing says why in a snackbar — a transaction changed since the AI agent asked, one no longer exists, or the transfer was refused —, as does an answer that came too late or a portfolio that could not be written; the state is read again.

**AGT-093 — An AI agent replaces four transactions AI agents recorded with a transfer (backend)**: A connected AI agent may call `replace_with_transfer` — `transactions` and a `rate`, each of the shape AGT-090 reads and refused as it refuses a wrong shape. Each of the four must carry a mark (AGT-045), whichever session recorded it: an id with no mark, or that no transaction has, is refused with `NotYourRecording` (AGT-051). What the four must be, the transfer they become and the checks before anything is written are AGT-090's, with their codes. The call asks nothing: it replaces them in one write (AGT-091), the transfer's parts marked with this session in that write (AGT-045), publishes `TransactionUpdated` once (AGT-036), and is answered `{"status": "replaced", "transfer": <the transfer as TRF-060 reads it>}`. It is refused with `TransactionChanged` for one of the four that changed, or a transfer that would move another cost, between the check and the write, with `TransactionNotFound` for one of the four removed in that gap, and with `DatabaseError` for a write that fails, nothing written in both; `DatabaseError`, its reason saying the transfer was recorded, when it was but could not be read back. Like a recording (AGT-049), once started it runs to its end. Each part takes a place of the session's limit and counts in what the window is told, as `record_transfer`'s do, the session's last recording being its transfer in (AGT-065A, AGT-047, AGT-052, AGT-084); nothing gives a place back, and a transfer whose parts would not all fit is refused before it is recorded. `preview_recording` does not take it (AGT-072): the checks are the call's own. Its title is "Replace four AI agent recordings with a transfer".

## Cross-amendments

- **CLI-030** — the command line records only while the window is closed; an AI agent works only while it is open. The two never write at once.
- **CLI-010** — `--mcp` is one of the program's starts without a window (AGT-012).
- **TRF-020, TRF-021, TRF-022, TRX-034** — four transactions the owner typed are replaced with a transfer on the owner's answer (AGT-091), and four AI agents recorded with none and the parts marked (AGT-093), by their removal from both accounts, as if never recorded, and the transfer's recording, in one write.
- **TRX-031, TRX-034, TRX-061** — an AI agent's correction and cancelling, the owner's removal of a session's recordings, and the removal or the change of a transaction the owner typed on the owner's answer, are the window's correction and deletion (AGT-050, AGT-053, AGT-081, AGT-088); a correction keeps a typed total as AGT-055 states.
