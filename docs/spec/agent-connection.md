# Business Rules — Agent Connection (AGT)

## Context

An agent — Claude Code, Claude Desktop, any program that speaks the Model Context Protocol — may read the portfolio and record in it through the application its owner has opened. The agent starts the installed program with `--mcp`; that process is a **bridge**: it holds no data and passes each tool call to the running application (ADR-023). The **channel** is what the application listens on; a **connection** is one bridge's link to it. The running application asks its owner before serving a connection and runs every tool through the queries and the recording rules the window uses. Nothing answers when the application is closed or when the owner's setting is off. The text an agent reads is English, like the command line's.

The agent connection exists on Linux and other Unix systems, and on Windows. A system without a local channel of either kind has none (AGT-023).

## Business Rules

### The bridge (010–019)

**AGT-010 — The bridge speaks the Model Context Protocol (backend)**: The program started with `--mcp` reads JSON-RPC messages, one per line, on its standard input and answers on its standard output until the input ends. It answers `initialize` (with the protocol version the agent asked for, the capability `tools`, and its name and version), `ping`, `tools/list` (the tools of AGT-046, each with a title, a description, the JSON schema of its arguments and whether it only reads — AGT-013) and `tools/call`; a notification takes no answer; any other method, and a call of a tool it does not list, is a JSON-RPC error. A line that is not JSON is skipped.

**AGT-011 — No application, no answer (backend)**: The bridge opens no database and reads no file of the portfolio (ADR-023). When no application answers on the channel — it is closed, or its setting is off — the bridge still introduces itself and lists its tools, and a tool call is answered with a refusal saying that Folioneer is not open or that agents are not allowed to connect.

**AGT-012 — `--mcp` starts the bridge (backend)**: `--mcp` as the program's first argument starts the bridge and nothing else: no window, no command of the command line (CLI-010), no scheduled download. Anywhere else among the arguments it does not start the bridge: the first argument decides, as CLI-010 says.

**AGT-013 — Each tool has a title and says whether it only reads (backend)**: In the list of tools, whatever the protocol version the agent asked for, each one carries a `title` — a few English words the owner reads in the agent client, "Record a purchase": never empty, and no two tools share one — and, under `annotations`, `readOnlyHint`: true for a tool that only reads the portfolio (AGT-040, AGT-070, AGT-071), false for every tool that records, corrects, cancels, adds, or asks to remove or to change (AGT-044, AGT-050, AGT-060, AGT-062, AGT-063, AGT-064, AGT-080, AGT-087). It is what lets an agent client ask the owner before a recording and not before a read; the owner's consent in the window (AGT-032) does not depend on it. The same statement decides what counts as a read of the session (AGT-052), so a tool is never a read for the client and a recording for the window. No other annotation is given: a client reads the absent ones by the protocol's defaults.

### The channel (020–029)

**AGT-020 — One request, one answer, one line (backend)**: The bridge and the application exchange JSON objects, one per line: the bridge asks to connect or calls a tool; the application answers that the connection is granted, with a tool's result, or with a refusal carrying a code and a reason. The code stays on the channel: the bridge passes the agent the reason, which is a full sentence, so a rule that names a refusal's code names what the application answers, not what the agent reads. A line that is no such object, or that is longer than 4 MiB — a tool's result included — ends the connection.

**AGT-021 — The channel is the owner's user's alone (backend)**: On Linux and other Unix systems the channel is a socket in a folder of the application's data folder. The folder is created for the owner's user alone (no permission for the group or for others), whatever the data folder allows, so no other user's program can reach the socket — the one thing of the data folder the bridge opens. On Windows the channel is a named pipe: its access list names the owner's user and nobody else, so the system refuses any other user's program that tries to open it, and it refuses clients of another computer; its name is drawn at each opening and written to a file of the same folder of the data folder, the one thing of the data folder the bridge opens. There the folder is not closed further: it takes the access list of the data folder, which is the owner's alone where the system puts it. The bridge opens only a name made of `\\.\pipe\folioneer-agent-` followed by letters, digits and dashes, and reads at most 256 bytes of the file. On both systems the application checks that the program at the other end runs as the same user and turns away one that does not, which is written to the log; on Windows the bridge checks the same of the program that answers, so a pipe another user opened under a name left by an earlier run is not spoken to. A file that names no pipe of the channel, or a pipe another user's program answers on, is to the agent an application that is not open (AGT-011). The channel is never a network port.

**AGT-022 — The channel exists only while the owner allows agents (frontend + backend)**: The setting "Allow agents to connect" is off until the owner switches it on, and is kept on this computer across restarts. With it off no channel exists. Switching it on opens the channel; the application opens it at start when the setting is on. Switching it off removes the channel and ends every grant (AGT-035). The settings page shows the setting with what it means.

**AGT-023 — A system without a channel has no agent connection (frontend + backend)**: Linux, the other Unix systems and Windows have a channel (AGT-021); the rule holds for a system the channel is not written for. Where the application has no local channel, the setting cannot be switched on (`NoAgentChannel`), the settings page shows it disabled and says the agent connection is not available on this system yet, and the bridge answers as AGT-011 says.

**AGT-024 — A channel that cannot be opened leaves the setting off (backend)**: A socket left by an earlier run — on Windows, the file naming its pipe — is replaced; so is, on Windows, a name whose pipe another user's program answers on. The channel is not opened in four cases: its folder is a symbolic link (on Windows, a junction too), its folder cannot be created, its socket — or its pipe, or the file naming it — cannot be created, or a running application of the owner's user still answers on its socket or its pipe — that application keeps its channel. On Windows two applications opening at the same moment are told apart by a lock on the file naming the pipe: the second finds the first one's pipe. Switching the setting on is then refused with `AgentChannelFailed`, the setting stays off, and the cause is written to the log. At start, with the setting kept on, the same cases leave the setting as it is and no channel: the cause is written to the log, and nothing listens until the application starts again or the owner switches the setting off and on. An application that opened no channel removes none when it closes.

### Consent (030–039)

**AGT-030 — A connection waits for the owner (backend)**: The bridge asks to connect at an agent's first tool call, under the name the agent gave for itself. The application answers only when its owner has: nothing is granted by default or after a delay, and the agent's call waits as long as the owner's answer does. An agent that goes away before the answer withdraws its request.

**AGT-031 — Nothing runs before the owner allowed (backend)**: A tool call on a connection the owner has not allowed is refused and reaches no tool. A refusal ends that request; the bridge then closes its connection, so the agent's next call asks again.

**AGT-032 — The owner allows or refuses in the window (frontend + backend)**: While an agent waits, a dialog shows over whatever view is open: the agent's name, the user it runs as — the application's own, the only one whose programs can connect (AGT-021) — the time it asked, what a yes covers — reading the accounts, the assets, the holdings, the transactions (AGT-070), the prices (AGT-071) and the totals, adding the assets the portfolio does not have yet, counted in the same limit (AGT-064), and recording opening balances, purchases, sales, deposits, withdrawals, dividends, splits, free shares and prices, up to the session's limit (AGT-044, AGT-060, AGT-063, AGT-062, AGT-047) — that one answer covers the whole session, and what it never covers: changing or removing a transaction the owner typed — the session corrects or cancels only what it recorded itself (AGT-050), and for a transaction the owner typed it can only ask, one at a time (AGT-080, AGT-087) — and reading a file, a setting or the sync folder. Its two actions are "Allow for this session" and "Refuse". It is easy to refuse and hard to approve blindly: refusing is the filled action and has the focus; "Allow" is inactive for a moment after the dialog appears; the keyboard's focus stays on the two actions; and the dialog closes only by an answer — neither its corner nor its backdrop dismisses it. A refusal gives the agent nothing: its call is answered that the connection was refused. Several agents waiting are shown one at a time, oldest first.

**AGT-033 — One grant covers the session (frontend + backend)**: Once allowed, the agent's calls on that connection are served without another question, and each is counted. While an agent is connected the header says so — "{agent} is connected" — on every view; a long name is shown cut, with the whole name as its hint. Nothing of a grant is remembered once the session ends, except on what it recorded (AGT-045).

**AGT-034 — The owner disconnects, or the agent leaves (frontend + backend)**: The header offers "Disconnect" beside each connected agent. Disconnecting closes that agent's connection, before anything it already sent is read: its next call is answered that Folioneer closed the connection, and the one after asks to connect again. The channel and the other agents' connections are untouched. An agent that goes away ends its own session.

**AGT-035 — Closing the application or the setting ends every grant (backend)**: When the setting is switched off, every request is refused, every session ends, every connection is closed — one that had not asked yet included — and the channel is removed, the file naming the pipe with it. When the application closes, the requests, the sessions and the connections end with it; the socket file, or the file naming the pipe, may stay, answers nothing — a bridge that tries it is told the application is not open (AGT-011) — and is replaced at the next start (AGT-024). No request is shown and no session opens afterwards, even for an answer given at that moment.

**AGT-036 — The window shows what the core holds (frontend + backend)**: The window reads the state of the agent connection (see Entity Definition). Every change — the setting, a request, a session, a tool call, the owner's removal of what a session recorded (AGT-053), a removal or change request arriving, answered or withdrawn (AGT-081, AGT-088) — publishes `AgentConnectionChanged`, on which the window reads the state again. Each write publishes its own event before that: `AssetUpdated` for an added asset; `TransactionUpdated` for a recording, a correction, a cancelling, each transaction of the owner's removal (AGT-053), the transaction removed on the owner's answer (AGT-081) and the transaction changed on the owner's answer (AGT-088); `AssetPriceUpdated` for a price. A recording that cannot be marked publishes its event when it is written and again when it is undone, though the call is refused (AGT-049). The window is told every one, in order, as it is told what the owner types: a view that shows what was written shows it at once, without the owner leaving it and coming back (B45).

**AGT-037 — An agent's name is text the application did not write (backend)**: The name an agent gives is cleaned before it is shown or logged, by the bridge and again by the application, since a program may speak to the channel without the bridge: control characters and the invisible characters that reorder or hide text are removed, it is cut to 60 characters, and an empty one becomes "An agent".

**AGT-038 — Limits (backend)**: At most 8 bridges are connected at once and at most 4 agents wait for the owner's answer; one more is turned away, and its call is answered as a refusal. A connection that has not asked to connect within 30 seconds is closed.

**AGT-039 — An answer that comes too late (frontend + backend)**: Answering a request that was withdrawn is refused with `ConnectionRequestGone`; disconnecting a session that already ended, with `SessionAlreadyEnded`. The window says so and reads the state again.

### Tools (040–049)

**AGT-040 — The read tools (backend)**: A connected agent may call four tools, each a query the window makes, answered as JSON text: `portfolio_summary` — each account with its total value, its unrealized gain and its performance this year, and the portfolio total (ACC-021, ACC-027); `list_accounts` — the accounts by name with their currency (CLI-018); `list_assets` — the assets a holding can be of, never a Cash Asset, with the fields of the command line's asset rows (CLI-021), the archived ones too when `archived` is true; `list_holdings` — the holdings of the account named by `account` with their figures and the account's totals (ACD), as they stood on the date `as_of`, today or earlier, when it is given. Amounts and quantities are the core's micro-units, which each description says. The schemas declare no other argument; one that arrives all the same is ignored.

**AGT-041 — Every call is written to the log (backend)**: Each tool call is written to the application's log with its session, its tool and whether it was refused; a connection allowed or refused is written with the agent's cleaned name (AGT-037).

**AGT-042 — A refusal names only what the agent sent (backend)**: The reason of a refusal repeats what the agent sent and never lists the accounts or the assets that exist — the list tools are how to ask.

**AGT-043 — The refusals of the read tools (backend)**: `list_holdings` names its account by its name, case ignored: a name that matches no account is refused with `AccountNotFound`, one that two accounts share with `AccountAmbiguous`, a missing one with `MissingArgument`; an `as_of` that is not a date, or is in the future, with `InvalidDate`. A read that fails is refused with `DatabaseError`, in any of the four tools.

**AGT-044 — Opening balances, purchases and sales (frontend + backend)**: A connected agent may record what the command line records, through the same recorder and the same rules as the window (CLI-012): `record_opening_balance` — the quantity and the total cost of what an account already held (TRX-047); `record_purchase` and `record_sale` — a quantity with either the unit price in the asset's currency or the broker's all-in total in the account's currency (CLI-013), and optionally fees, an exchange rate and a note of at most 500 characters. Each names its account by name and its asset by name, reference, ISIN or reference with its exchange (CLI-011). What is left out is as on the command line (CLI-014): the date is today, the fees 0, the rate 1. A recording is answered with the transaction as recorded, its account, its currency and its asset. The window shows it as it happens, by the event every recording publishes.

**AGT-045 — What an agent recorded is marked (frontend + backend)**: A transaction an agent recorded is marked with the agent's name, the key of its session and the time that session started; a transaction without a mark is one the owner typed, one an agent recorded on another of the owner's computers — the mark is kept on the computer that recorded it and is not sent to the others — or, should both the marking and its undoing fail, the one AGT-049 names. The rows of the account journal carry the mark (TXL-060), and the journal shows it in a column "Recorded by": the agent's name, with "{agent} · session of {date and time}" as its hint (TXL-061). The mark goes with its transaction: correcting the transaction keeps it, removing the transaction removes it.

**AGT-046 — No other tool exists (backend)**: The tools are the four of AGT-040, the one of AGT-070, the one of AGT-071, the three of AGT-044, the two of AGT-050, the three of AGT-060, the two of AGT-063, the one of AGT-062, the one of AGT-064, the one of AGT-080 and the one of AGT-087. Nothing corrects or deletes a transaction the session did not record itself — a transaction the owner typed is removed or changed only by the owner's answer (AGT-080, AGT-087) —, creates an account, changes or removes an asset, or takes or returns a path, a setting or anything of sync.

**AGT-047 — A session records up to a limit (backend)**: One session records at most 500 transactions and prices (AGT-062), the assets it adds counted with them (AGT-064), in all. The next recording, or the next asset added, is refused with `SessionLimitReached`, which says the owner disconnects and allows a new session to go on; reading is not limited.

**AGT-048 — The refusals of a recording (backend)**: Figures are decimals with a dot and at most six decimals, as text or as JSON numbers; anything else is refused with `InvalidFigure`; a missing figure, account or asset with `MissingArgument`. An argument a recording does not know is ignored, as for the read tools (AGT-040). A price together with a total, or neither, a `date` or a `note` that is not text, and a note that is too long are refused with `InvalidArguments` — a date that is not text is never read as today. Every other refusal is the recording's own, with its code and its reason: the account or the asset not found or ambiguous (CLI-011), a date that is text but not a date (`InvalidDate`) or is in the future (`DateInFuture`), an oversell, and the rest of the window's rules (CLI-012).

**AGT-049 — A recording that cannot be marked is undone (backend)**: Recording and marking are one operation of the core, which runs to its end once started: a disconnect or a closing application never stops it between its two writes. When the mark cannot be written the recording is undone and the agent is refused with `NotRecorded`: nothing was recorded. Should the undoing fail too, the refusal is `RecordedNotMarked`, which says the transaction was recorded and tells the agent to tell the owner; both failures are written to the log, and that transaction counts against the session's limit (AGT-047).

### Corrections and removals (050–059)

**AGT-050 — A session corrects and cancels what it recorded (backend)**: A connected agent may call two more tools, each naming a transaction by the id its recording returned: `cancel_recording` removes it, and `correct_recording` changes it, when it is an opening balance, a purchase or a sale (AGT-061) — the date, the quantity, the unit price or the all-in total (never both; for an opening balance the total is its total cost), the fees, the exchange rate, the note: what is given replaces what was recorded and the rest stays. When neither a price nor a total is given, the transaction's stored total is kept, taken as a typed total (TRX-061), while nothing it is made of changes; a new quantity, new fees or a new rate make the total follow the unit price instead (TRX-026) — except for an opening balance, whose total cost only a new total changes. The id is text, and a missing one is refused with `MissingArgument`; the figures, the `date` and the `note` are read as a recording's (AGT-048). A correction that gives nothing to change, both a price and a total, or — for an opening balance, which has none (TRX-047) — a price, fees or a rate, is refused before anything is changed. Both tools then run through the rules of the window's correction and deletion (TRX-031, TRX-034) and are refused with their codes. Like a recording (AGT-049), a correction or a cancelling runs to its end once started. Neither gives a place back of the session's limit, and a correction takes none (AGT-047).

**AGT-051 — A session touches nothing it did not record (backend)**: The two tools are refused with `NotYourRecording` for a transaction the owner typed, for one another session recorded — an earlier session of the same agent included — and for one that does not exist; the reason is the same sentence in the three cases, so it says nothing of what exists (AGT-042). "Its own" is the mark's session (AGT-045), not the agent's name: a name is what the agent says of itself.

**AGT-052 — The window is told what a session did (backend)**: With each session the state (AGT-036) carries when the owner allowed it, how many of its calls of a read tool (AGT-013) were answered, how many of the transactions it recorded still exist — whatever removed the others: the session, the owner's removal (AGT-053) or a deletion in the journal — and, of those that exist, the type, the asset's reference and the date of the one it recorded last, as they stand after any correction. The two are read from the portfolio after each recording, correction and cancelling of the session and after the owner's removal, so a deletion made in the journal shows at the next of these. The window is told after every call and after the owner's removal.

**AGT-053 — The owner removes everything a session recorded (backend)**: For a session that is still connected the owner can remove, in one action, every transaction it recorded and that exists when the action starts, and nothing else: each goes through the deletion of the window (TRX-034), the last recorded first, and one the deletion refuses is tried again once the others are gone. What the deletion still refuses — a recording that a transaction recorded since depends on, the owner's or another session's — is kept and counted, and the action answers how many were removed and how many kept; a recording the session makes while the action runs stays, and counts in what the window is told afterwards. For a session that has ended, or that never was, the action is refused with `SessionAlreadyEnded` and nothing is removed (AGT-039). When the portfolio cannot be read or written the action fails with `DatabaseError`; what it removed before stays removed, and the window is told what is left. Once the session has ended its recordings stay marked in the journal (AGT-045) and are removed one by one there.

**AGT-054 — The session dialog (frontend)**: In the header, "{agent} is connected" (AGT-033) opens a dialog on that session, over the whole window. It shows since when the agent is connected, how many of its calls of a read tool were answered — shown as requests — how many assets it added with the name and the reference of the last one, or that it added none (AGT-064), how many transactions it recorded that still exist, and its last recording — its type, the asset's reference and its date — or that there is none (AGT-052); the figures follow the state as it changes (AGT-036). Its three actions are "Remove everything it recorded", "Close" and "Disconnect" (AGT-034); a sentence says what the first removes — the session's recordings as they stand, a correction the owner made to one of them included, and no transaction the owner recorded — and that it asks to confirm. The sentence speaks of transactions only: it does not name the assets the session added, which the removal leaves (AGT-064). With no recording left the removal is inactive and the sentence says so. Removing asks in a second dialog, which names the agent and the number of transactions as it stands then: keeping them is the filled action and has the focus, and only "Remove" there removes (AGT-053). The removal runs behind the session dialog, whose actions stay active. What it did is said in a snackbar: how many transactions were removed and, when some were kept, how many, because a transaction recorded since depends on them. A refusal (`SessionAlreadyEnded`) or a failure (`DatabaseError`) is said in a snackbar too, and the state is read again: after a failure the dialog's figures show what is left. Both dialogs close when the session ends. A connection request that arrives meanwhile takes their place until it is answered (AGT-032).

### Cash, dividends, prices, splits, free shares and assets (060–069)

**AGT-060 — Deposits, withdrawals and dividends (backend)**: A connected agent may record three more transactions, through the same recorder and the same rules as the command line (CLI-027, CLI-028): `record_deposit` and `record_withdrawal` — an account by its name and an amount in the account's currency, and no asset; `record_dividend` — an account, a paying asset named as in AGT-044, the total net amount received in the asset's currency and optionally the exchange rate to the account's currency (default 1, CLI-014). Each takes optionally a date (default today) and a note. The figures, the date, the note and what is missing are read and refused as a recording's (AGT-048). Each is answered as a recording is (AGT-044) — the asset being `null` for a deposit or a withdrawal — marked (AGT-045), counted against the session's limit (AGT-047), undone when it cannot be marked (AGT-049), told to the window (AGT-052) — the asset of a deposit or a withdrawal being the account's Cash Asset — cancelled by `cancel_recording` (AGT-050) and removed with the session's recordings (AGT-053). The refusals are the window's (CLI-012), among them `AmountNotPositive`, `InsufficientCash` for a withdrawal that would leave the account's cash below zero, today or at any point from its date on (CSH-031, CSH-080), and `AssetNotHeld` for a dividend of an asset the account does not hold today, whatever the date (DIV-011).

**AGT-061 — Only an opening balance, a purchase or a sale is corrected (backend)**: `correct_recording` refuses a deposit, a withdrawal, a dividend, a split or free shares (AGT-063) the session recorded with `InvalidArguments`, saying to cancel it and record it again. A transaction the session did not record is answered `NotYourRecording` first (AGT-051), so the refusal never says what kind of transaction another's is.

**AGT-062 — A price at a date (backend)**: A connected agent may call `record_price` — an asset named as in AGT-044, the price of one unit in the asset's currency, and optionally a date (default today); it names no account. The figure and what is missing are read and refused as a recording's (AGT-048), and so is a date that is not text. The price is written with the source `Agent`, which is its mark (MKT-103): it shows wherever a price's source does, on this computer and on the owner's others. The latest write wins, as for every price: it replaces the price the asset already has on that date, typed or fetched, and the next write on that date replaces it in turn (MKT-103). The refusals are a price's own: `NotPositive`, `DateInFuture`, `InvalidDateFormat` for a date that is text but not a date, `Archived`. It is answered with the price as stored, the asset's reference and its currency, and takes one place of the session's limit (AGT-047). A price is no transaction: it is not counted in what the window is told of the session (AGT-052), `correct_recording` and `cancel_recording` do not name it (AGT-050), and "Remove everything it recorded" leaves it (AGT-053) — the owner edits or deletes it in the price history.

**AGT-063 — Splits and free shares (backend)**: A connected agent may record two more transactions, through the same recorder and the rules of the window: `record_split` — an account and an asset named as in AGT-044, and the split's size as a ratio, `new` shares for every `old` shares held, of which the factor recording stores is made as in the window (SPL-062) — and `record_free_shares` — an account, an asset and the quantity received, a figure read as a recording's (AGT-048). Each takes optionally a date (default today) and a note. A part of the ratio is a whole number, given as a JSON number or as text of digits, a sign before them and spaces around them allowed: a missing one is refused with `MissingArgument`; one that is anything else — a decimal, `2.0` included, a number too large to hold, a value that is neither text nor a number — with `InvalidFigure`; one that is zero or below, and a ratio whose factor rounds to nothing or cannot be held, with `SplitFactorNotPositive` (SPL-062). The date, the note and what else is missing are read and refused as a recording's, and the account and the asset not found or ambiguous as well (AGT-048). The other refusals are the window's, with their codes, among them: for a split, `SplitFactorIsOne`, `SplitCollapsesPosition`, `ClosedPosition` and `CascadingOversell` (SPL-011, SPL-021, SPL-022); for free shares, `QuantityNotPositive` (FSD-011); for both, `AssetNotHeld` for an asset the account does not hold today, whatever the date. The account's cash is never named (CLI-011): a split or free shares of it is refused with `AssetNotFound`, so the window's `SplitOnCashAsset` and `FreeSharesOnCashAsset` (SPL-012, FSD-011) are not reached through the tool. A split records no price — the price the window's form offers to record is the form's (SPL-040): the tool's description tells the agent to record the price after the split with `record_price`. Each is answered as a recording is (AGT-044), marked (AGT-045), counted against the session's limit (AGT-047), undone when it cannot be marked (AGT-049), told to the window (AGT-052), cancelled by `cancel_recording` (AGT-050) through the window's deletion with its refusals (SPL-030, FSD-041) — among them a later sale left without enough shares — removed with the session's recordings (AGT-053), and never corrected (AGT-061), where the window corrects both (SPL-030, FSD-040).

**AGT-064 — An asset the portfolio does not have (frontend + backend)**: A connected agent may call `add_asset` — a name, a reference, a currency and either a kind, a class or both, and optionally an ISIN and the MIC code of an exchange; kind, class and exchange are read with case ignored. It adds the asset through the rules of the window's form, as the command line does (CLI-026): the kind is one a user may create an asset of — `Listed`, `Crypto`, `Custom` (AST-037) — or is decided by the core (AST-034); the class is one a user may create an asset in (CSH-015), never `Cash`, and left out it is the one the core preselects for the kind; the risk level and the category are the core's defaults and the asset bears no interest. The tool takes no other argument, and one that arrives all the same is ignored (AGT-040). A name, a reference or a currency that is missing, empty or not text, and neither kind nor class, are refused with `MissingArgument`. The name and the reference are text an agent wrote that the portfolio keeps and the window shows: a name longer than 100 characters, a reference longer than 30, and either holding a control character or one of the invisible characters that reorder or hide text (AGT-037) are refused with `InvalidArguments`. So are a kind or a class that is not one of those above, `Cash` included, and a kind, a class, an ISIN or an exchange that is not text. The other refusals are the form's, with their codes, among them `AssetAlreadyExists` for an asset the portfolio already has, archived or not (AST-032) — its reason says so and does not name the existing asset (AGT-042) — `IsinRequired`, `IsinNotAllowed`, `ExchangeNotAllowed` and `ClassNotAllowed` (AST-031), `InvalidCurrency`, `InvalidIsinFormat` and `InvalidExchange`. It is answered with the asset as `list_assets` gives it and whether another asset shares its reference (CLI-041), and the window's views of assets show it as it happens, by the event an asset's creation publishes. An added asset takes one place of the session's limit, and at the limit the addition is refused (AGT-047); a refused addition takes none. It carries no mark: the state (AGT-036) says, for the session while it is connected, how many assets it added — additions counted as they are made, whatever becomes of the asset afterwards — and the name and the reference of the last one as it was added; the session dialog shows them (AGT-054), and nothing of it is kept once the session ends. An asset is no transaction: `correct_recording` and `cancel_recording` do not name it, "Remove everything it recorded" leaves it (AGT-053), and the owner edits, archives or deletes it among the assets. The connection dialog names adding assets in what a yes covers, on a line of its own (AGT-032).

### More reads (070–079)

**AGT-070 — The transactions of an account (backend)**: A connected agent may call `list_transactions` — an account by its name (AGT-043) and optionally an asset named as in AGT-044, `from` and `to`, two dates that bound the transactions' dates, both included, a `transaction_type` — `Purchase`, `Sell`, `OpeningBalance`, `Deposit`, `Withdrawal`, `Dividend`, `FreeShares`, `ManagementFee`, `Split` or `Interest`, case ignored — `recorded_by` — `owner`, `agent` or `session`, case ignored — and a `page`, a JSON whole number from 1. The tool takes no other argument, and one that arrives all the same is ignored (AGT-040). It reads the account journal the window reads (TXL-060) and writes nothing. The transactions the filters keep are answered oldest first — by date, then in the order entered — 100 to a page, the first page when none is asked, with the account's name and currency, how many transactions the filters keep in all, the page and how many pages they make — none when they keep no transaction; a page past the last holds no transaction. A `from` later than `to`, or dates in the future, keep none and are not refused. Each transaction carries its id — the one `correct_recording` and `cancel_recording` take (AGT-050) — its date, its `transaction_type`, written as above, the reference of its asset, or `null` for a transaction on the account's cash, and its quantity, unit price, total, fees and exchange rate as stored, in micro-units — a figure the transaction does not have is 0, and the quantity of a split is its factor (SPL-010) — and its note. Each says who recorded it, read from the mark this computer holds (AGT-045): `owner` for a transaction without a mark — the owner's, and also one an agent recorded on another of the owner's computers, whose mark stays there — `session` for one this session marked, `agent` for one another session marked. The filter `recorded_by` keeps `owner` the transactions without a mark, `agent` every transaction an agent marked, this session's included, and `session` this session's alone. Whatever the filter, a marked transaction comes with the agent's name, cleaned when its session opened (AGT-037), and when that session started, as the journal's "Recorded by" shows them (TXL-061). The refusals are a read's: a missing account with `MissingArgument`, the account or the asset not found or ambiguous (CLI-011), a `from` or a `to` that is not a date — not text included — with `InvalidDate`, an asset, a `transaction_type` or a `recorded_by` that is not text or not one of those above, and a page that is not a whole number from 1 — text of digits included — with `InvalidArguments`, a read that fails with `DatabaseError`. It is a read: it says it only reads (AGT-013), each answered call counts as one of the session's reads (AGT-052), and it takes no place of the session's limit (AGT-047). The notes it returns are text the owner or an agent typed, given as they are.

**AGT-071 — The price of an asset at a date (backend)**: A connected agent may call `get_price` — an asset named as in AGT-044, archived or not, and optionally a `date` (default today); it names no account, and an argument it does not know is ignored (AGT-040). It answers the price the application holds for that asset at that date (MKT-104), in five members: `status`, `priced`; the asset's reference; its currency; the `date` asked; and `price`, the price of that date or the closest earlier one as stored — its own date, which is its observation date, the price of one unit in micro-units, and its source: `Manual` for a price the owner typed, `Agent` for one an agent recorded, or the provider it was fetched from (MKT-100). When the asset has no price up to that date the answer is the same five members, with `status` `no_price` and `price` `null`: it is an answer, not a refusal. The refusals are a read's: a missing asset with `MissingArgument`, the asset not found or ambiguous (CLI-011), a `date` that is not a date — not text included — or is in the future with `InvalidDate`, a read that fails with `DatabaseError`. It is a read: it says it only reads (AGT-013), each answered call counts as one of the session's reads (AGT-052), and it takes no place of the session's limit (AGT-047).

### Removal and change requests (080–089)

**AGT-080 — An agent asks to remove a transaction the owner typed (backend)**: A connected agent may call `request_removal` — a transaction by its id, as `list_transactions` gives it (AGT-070), as text; one that is missing or not text is refused with `MissingArgument`. A transaction the owner typed is one with no mark on this computer (AGT-045): the one `list_transactions` says `owner` recorded. The call is refused before anything is asked with `TransactionNotFound` for an id no transaction has, and with `NotTypedByOwner` for a transaction an agent recorded — the session cancels its own with `cancel_recording` (AGT-050), and another session's is not its to touch (AGT-051). Unlike AGT-051, the two are told apart: `list_transactions` already says which transactions exist and who recorded each. A portfolio that cannot be read is refused with `DatabaseError`. Otherwise the call waits for the owner's answer (AGT-081) and is answered: `{"status": "removed", "transaction": <id>}` when the owner removed it; `RemovalRefused`, and nothing else, when the owner refused or the session ended first (AGT-082); and, when the owner answered yes and it was not removed, the code and reason of why — `TransactionChanged` for a transaction that no longer stands as the owner was shown it, `TransactionNotFound` for one deleted meanwhile, the deletion's own code for one a later transaction depends on, `DatabaseError`. A session asks one at a time: its connection serves its calls in turn, so its next call waits for this one's answer. Two sessions may ask for the same transaction; once it is removed, the other's yes answers `TransactionNotFound`. The call records nothing and is not counted against the session's limit (AGT-047). Its title is "Ask to remove a transaction you typed".

**AGT-081 — The owner answers each removal (backend)**: While a removal request waits, the state (AGT-036) carries it, oldest first, with the agent's name, when it asked, and the transaction as it stood when the agent asked: its date, its account's name, its type, its asset's name and reference — none for a transaction on the account's cash —, its quantity as stored — a split's is its factor, as `list_transactions` gives it —, and its total in the account's currency, with that currency. The owner answers in the window: remove it, or refuse. A yes goes through the deletion of the window (TRX-034), and only while the transaction stands as it was shown — the same date, type, quantity and total —; the transaction removed publishes `TransactionUpdated` (AGT-036). The request is gone once answered, whatever came of it, and its agent is told (AGT-080). The owner's answer to a request no longer waiting is refused with `RemovalRequestGone`; a yes that removed nothing is refused with `TransactionNotRemoved` and the reason's code as the agent is given it, or with `DatabaseError` when the portfolio could not be read or written.

**AGT-082 — Nothing of an answer is kept (backend)**: The session's grant (AGT-032) never covers a removal or a change: every one is asked, and an answer covers the one transaction it was asked for — for a change, that one change. Nothing of an answer is remembered for the next request, the same transaction's included. A request is withdrawn when its session ends — the owner disconnects it or switches the setting off (AGT-034, AGT-035), and its call is answered `RemovalRefused` or `ChangeRefused` before its connection closes — and when its agent goes away while it waits (AGT-086).

**AGT-083 — The removal dialog (frontend)**: While a removal request waits and no agent waits to connect — a connection request comes first (AGT-032) — a dialog shows over whatever view is open, and the session dialog gives way to it as to a connection request (AGT-054). Its title is "{agent} asks to remove a transaction you typed". It shows the transaction in full, as the state carries it (AGT-081): its date, its account, its type, its asset with its reference, its quantity, and its total with the account's currency. A transaction on the account's cash shows no asset and no quantity. A split's quantity is its factor; a total of 0 is shown as 0. It says what would become of it — removed, the account's holdings and cash recomputed from the transactions that remain — and that the answer covers this transaction only. Its two actions are "Remove this transaction" and "Refuse"; no action covers more than one. Refusing is the filled action and has the focus; "Remove this transaction" is inactive for the same moment as "Allow" (AGT-032); the keyboard's focus stays on the two actions; neither its corner nor its backdrop dismisses it: it closes on an answer, or when its request is withdrawn (AGT-082). Several requests are shown one at a time, oldest first. A removal says nothing more: the views that show the transaction follow it (AGT-036). A yes that removed nothing says why in a snackbar — the transaction changed since the agent asked, it no longer exists, or a later transaction depends on it —, as does an answer that came too late or a portfolio that could not be written; the state is read again.

**AGT-084 — The window says what an agent records (frontend + backend)**: With each session the state (AGT-036) carries how many transactions it recorded, whatever became of them since — a count that only rises, unlike how many still exist (AGT-052): a price, an added asset and a refused recording are not counted in it. Whatever view is open, each read of the state that finds this count risen since the last read says the session's last recording in the window's snackbar: "{agent} recorded: {type} · {asset} · {date}" — the transaction's type, the asset's reference and the date, as the session dialog shows its last recording (AGT-054); and each read that finds the session's count of added assets risen (AGT-064) says the last of them: "{agent} added an asset: {name} ({reference})". The agent's name is shown as it is held (AGT-037). The recording message names the session's last recording that still exists (AGT-052): when none is left, nothing is said. Several recordings between two reads make one message, about the last. A read says the sessions oldest first, a session's recording before its added asset, and each message replaces whatever the snackbar showed, so the last one said stays. A session that ended before the read is not announced. A correction or a cancelling moves neither count and is not announced, nor is a session the window reads for the first time. A price an agent records is not announced: the state does not carry it.

**AGT-085 — A call the agent gave up on (backend)**: While a call waits, the bridge still hears its agent. A cancel (`notifications/cancelled`) naming the tool call being answered, while the bridge holds no grant for its connection, gives that call up: the connection request is withdrawn, so its dialog leaves the window, which shows one only while an agent waits (AGT-032, AGT-036); the call takes no answer, and the next call asks again. Once the bridge holds the grant, a cancel changes nothing: the call — a removal or change request waiting on the owner included (AGT-080, AGT-087) — is answered, and the session stays. When the owner's yes and the cancel cross, the order in which the application reads them decides: a yes read first opens a session that ends as the connection closes (AGT-034). A cancel naming no call being answered is ignored. Anything else the agent says while a call waits is answered after it, in order; past 64 such lines the bridge stops reading the agent until the call is answered.

**AGT-086 — An agent that goes away mid-call (backend)**: An agent goes away when its bridge's input ends. While a call waits it ends the bridge: a connection request is withdrawn as when it goes away before the answer (AGT-030), and in a session the call is given up — a removal or change request it waits on is withdrawn (AGT-082) — and the session ends with its connection (AGT-034). A write already started — a recording, a correction, a cancelling, a price, an added asset — runs to its end (AGT-049); the window is told, and the call is written to the log as given up (AGT-041).

**AGT-087 — An agent asks to change a transaction the owner typed (backend)**: A connected agent may call `request_change` — a transaction by its id, read and refused as `request_removal` reads it (AGT-080), and what changes, as the window's correction of that type takes it (TRX-031 and the correction rules of each type — CSH-023, CSH-033, DIV-040, SPL-030, FSD-040, INT-040, FEE-063): a `date` and a `note` for every type; for a purchase or a sale a `quantity`, a `price` or a `total` — never both —, `fees` and a `rate`; for an opening balance a `quantity` and a `total`, its total cost; for a deposit or a withdrawal an `amount`; for a dividend an `amount`, in the asset's currency, and a `rate`; for a split `new` and `old`, its ratio as `record_split` reads it (AGT-063); for free shares, a management fee or interest a `quantity`. What is given replaces what is stored and the rest stays, a stored total kept or following the unit price as a correction keeps it (AGT-050). The figures, the `date` and the `note` are read and refused as a recording's (AGT-048), and an argument the tool does not know is ignored (AGT-040). Before anything is asked the call is refused: with `MissingArgument` for a missing id, when nothing is given to change, or when the transaction as it would become equals it as it stands in every value the state shows of it (AGT-088); with `TransactionNotFound` and `NotTypedByOwner` as `request_removal` is (AGT-080); with `InvalidArguments` for both a price and a total, for one part of a split's ratio without the other, or for an argument above that the transaction's type does not take, the reason naming those it takes; with each refusal the window's correction gives, checked on the account as it stands with nothing written — among them `CascadingOversell`, `InsufficientCash` and `DateInFuture` —; and with `DatabaseError` for a portfolio that cannot be read. Otherwise the call waits for the owner's answer (AGT-088) and is answered: `{"status": "changed", "transaction": <the transaction as stored after the change>}` when the owner changed it — its id, account, asset, date, type, note and, in micro-units, its quantity, unit price, total, fees and exchange rate, a split's quantity being its factor; `ChangeRefused`, and nothing else, when the owner refused or the session ended first (AGT-082); and, when the owner answered yes and it was not changed, the code and reason of why — `TransactionChanged` for a transaction that no longer stands as the owner was shown it, `TransactionNotFound` for one deleted meanwhile, the correction's own code, `DatabaseError`. A session asks one at a time, as for a removal (AGT-080). The call records nothing and is not counted against the session's limit (AGT-047): a transaction changed on the owner's answer stays the owner's, with no mark (AGT-045), and is counted in none of the session's figures (AGT-052, AGT-084). Its title is "Ask to change a transaction you typed".

**AGT-088 — The owner answers each change (backend)**: While a change request waits, the state (AGT-036) carries it with what a removal request carries (AGT-081) and the transaction as it would become, in the same form. A transaction the state shows — of a removal or a change request — carries its unit price, its fees, its exchange rate and its note besides what AGT-081 names. A change request also names the values the change moves among the date, the quantity, the total, the unit price, the fees, the rate and the note, so the window marks them without comparing (AGT-089). Removal and change requests share one order, oldest first. The owner answers in the window: change it, or refuse. A yes goes through the correction of the window (TRX-031) with what the agent asked, and only while the transaction stands in full as it was shown — the same date, type, quantity, total, unit price, fees, rate and note —; the transaction changed publishes `TransactionUpdated` (AGT-036). The request is gone once answered, whatever came of it, and its agent is told (AGT-087). The owner's answer to a change request no longer waiting is refused with `ChangeRequestGone`; a yes that changed nothing is refused with `TransactionNotChanged` and the reason's code as the agent is given it, or with `DatabaseError` when the portfolio could not be read or written.

**AGT-089 — The change dialog (frontend)**: A change request is shown as a removal request is (AGT-083), in the one order of the requests (AGT-088), with the same keyboard, focus and dismissal rules. Its title is "{agent} asks to change a transaction you typed". It shows the transaction in two columns, "As it is" and "As it would become", with the rows of the removal dialog, and a row for the unit price, the fees, the exchange rate or the note when the change moves it; a value the request names as moved (AGT-088) is struck through in the first and set in the accent colour in the second. The note is text the owner or an agent typed, shown as it is. It says what would become of it — changed as shown, the account's holdings and cash recomputed from it — and that the answer covers this change of this transaction only. Its two actions are "Change this transaction", inactive for the same moment as "Allow" (AGT-032), and "Refuse", the filled action in focus. A change says nothing more: the views that show the transaction follow it (AGT-036). A yes that changed nothing says why in a snackbar — the transaction changed since the agent asked, it no longer exists, or the correction refused it —, as does an answer that came too late or a portfolio that could not be written; the state is read again.

## Workflow

```
[Agent] ──starts──▶ folioneer --mcp (bridge: no data)
      │ initialize, tools/list                 answered by the bridge alone (AGT-010)
      │ tools/call ──▶ bridge ──connect──▶ channel ──▶ running application
      │                                                  │ setting off / closed → "not open" (AGT-011)
      │                                                  ▼
      │                                   dialog: Allow for this session / Refuse (AGT-032)
      │                                                  │ refused → nothing (AGT-031)
      │                                                  ▼ allowed
      │ ◀── result ── bridge ◀── answer ── tool run through the window's queries and rules (AGT-040, AGT-044)
      ▼
header: "{agent} is connected" · Disconnect (AGT-033, AGT-034)
```

## UX Mockup

### Entry point

**Settings** — "Allow agents to connect", under the sync line. The connection dialog and the header's indicator appear on their own.

### States

- **Setting off**: nothing listens; the checkbox says what switching it on allows.
- **Not available on this system**: the checkbox is disabled and says so (AGT-023).
- **An agent asks**: the connection dialog, refusing in focus (AGT-032).
- **Connected**: the header names the agent and offers to disconnect (AGT-033); the name opens the session dialog (AGT-054).
- **Session**: what the agent read, the assets it added and what it recorded, its last recording, and the removal of everything it recorded, confirmed in a second dialog where keeping is in focus; the outcome is said in a snackbar (AGT-054).
- **An agent asks to remove a transaction you typed**: the removal dialog, the transaction's date, account, type, asset, quantity and total, refusing in focus (AGT-083).
- **An agent asks to change a transaction you typed**: the change dialog, the transaction as it is and as it would become side by side, refusing in focus (AGT-089).
- **An agent records**: a snackbar names the agent and what it recorded or added, on every view (AGT-084).
- **Too late**: a request already withdrawn or a session already ended is said in a snackbar, and the state is read again (AGT-039).

## Cross-amendments

- **CLI-030** — the command line records only while the window is closed; an agent works only while it is open. The two never write at once.
- **CLI-010** — `--mcp` is one of the program's starts without a window (AGT-012).
- **TRX-031, TRX-034, TRX-061** — an agent's correction and cancelling, the owner's removal of a session's recordings, and the removal or the change of a transaction the owner typed on the owner's answer, are the window's correction and deletion (AGT-050, AGT-053, AGT-081, AGT-088).
- **CLI-011, CLI-012, CLI-013, CLI-014** — an agent's recordings name their account and asset, take the same defaults, are checked and are refused as the command line's are (AGT-044, AGT-048).
- **CLI-027, CLI-028, CSH-031, CSH-080, DIV-011** — an agent's deposits, withdrawals and dividends are the command line's, checked by the window's rules (AGT-060).
- **TXL-060, CLI-011** — an agent lists an account's transactions from the account journal the window reads, naming the account and the asset as a recording does (AGT-070).
- **TXL-060, TXL-061** — the rows of the account journal carry the mark, and the journal shows which agent session recorded a transaction (AGT-045).
- **SYN-023** — the marks are device-local data: they are never synced (AGT-045).
- **SPL-011, SPL-012, SPL-021, SPL-022, SPL-030, SPL-040, SPL-062, FSD-011, FSD-021, FSD-040, FSD-041** — an agent's split and free shares are the window's, checked by its rules; the split's factor is the one its ratio gives in the window, and no price is recorded with it; an agent cancels both through the window's deletion and corrects neither, where the window does (AGT-063, AGT-061).
- **CLI-026, CLI-041, AST-031, AST-032, AST-034, AST-037** — an agent adds an asset as the command line does, through the rules of the window's form (AGT-064).
- **MKT-104, MKT-100, CLI-011** — an agent reads an asset's price at a date as the core answers it, with its source, naming the asset as a recording does (AGT-071).
- **MKT-100, MKT-103, SYN-038** — a price an agent recorded carries the source `Agent`, a value of data format version 3 (AGT-062).
- **CLI-029** — the command line records a price by the same lookup and the same checks; both replace the price at that date; the command line's is the owner's own — source `Manual` — where an agent's is marked `Agent` (AGT-062).
- **ADR-023** — the bridge holds no data and the channel is never a network port.
